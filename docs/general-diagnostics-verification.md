# 通用故障辅助排查资料核验

日期：2026-10-23。依据用户最新范围，首版不要求具体品牌、车型、年款，先准备通用症状到故障类型、检查依据和换件判断的资料；本次没有实现 RAG/Agent 运行代码。

## 实际交付

data/knowledge/diagnostics/manuals 下7份 Markdown 正文，包含8条公共规则和15个症状条目。每个症状条目保留适用与追问、故障类型、检查路径、换件判断及依据限制。覆盖启动/充电、发动机不着车与失火、冷却、制动/ABS、空调送风制冷、雨刮和灯光。

manifest.json 保存正文 SHA256、文档版本、23个实际章节/条目 ID、来源与索引状态。sources.json 登记16个 DENSO、HELLA、VARTA 公开厂家页面及使用章节；未复制全文，未编造厂家版本号、技术批准或生效日期。编写规则与厂家原理参考分开表达。

part-type-map.json 将条目中的29种候选类型对应到现有目录 SKU、名称、单位和29张独立本地图片。映射仅作类型导航，不代表本次故障已确认、商品适配或实物需求；单次需求数量为空。当前未覆盖全部48类目录，目录外故障不能硬凑已有备件。

evals/diagnostics 下8题开发集、22题冻结验收集，共30题，含合成检查记录。覆盖15个症状、四种换件状态、资料不足、目录缺项、错误适配、实时库存边界、提示注入和无需换件情况。输入和预期已编写，尚未运行模型，也未生成评测成绩。评测集只作为后续实现的验收输入，不作为检索资料导入。

README.md 和 AGENTS.md 已同步简化范围；保留现有车型/适配能力，但它不再是通用排查的入口前提。实际选商品、数量或办理库存时的核准与确认要求仍然适用。

## 实际核验与结果

在项目根目录通过 PowerShell 将一次性标准库校验脚本传入项目独立解释器，实际执行命令入口为 .\.venv\Scripts\python.exe -X utf8 -。脚本使用 json、hashlib、re、ast、pathlib 检查文件；只读解析种子源码和图片白名单，未导入业务启动代码、未连接数据库。

核验全部通过：

- 7份正文的文件存在、UTF-8 解码、版本/ID、SHA256 与清单一致，无替换乱码字符；23个章节 ID 唯一。
- 15个症状条目均有五类完整上下文；除共同规则外，相关正文声明共用规则依赖；状态均为待技术复核、未索引且默认不检索。
- 16个来源 ID 唯一，引用均能关联来源条目，外部 URL 为 HTTPS 且无重复，章节与访问日期已登记。没有把缺失的厂家版本号编成项目版本。
- 29种类型逐项匹配现有种子/扩展目录的 SKU、原始名称、单位和图片键；本地图片均有 PNG 文件头，29个不同 SHA256；全部15个症状均有类型映射。此检查不等于实物适配核准。
- 30题题号唯一，预期引用均存在，约束的部件类型均在映射中；全部15个症状和四种换件状态均被覆盖；所有 execution_status 仍为 not_run。
- 正文未引入固定电压、电流、压力或磨损毫米数等统一维修数值；具体适用参数仍由实际维修资料确定。

上述是资料结构与引用核验，不是合格维修人员的技术审签，也不是诊断准确率测试。公开来源已在编写时在线查阅；未做长期可用性保证或厂家全文镜像。只改文档、JSON 和项目说明，因此未重复运行后端业务测试、前端构建或数据库迁移。未修改应用、数据库、依赖、现有图片和 .env，未创建 Git 提交。

## 后续执行顺序

先完成这批资料的技术复核和版本发布设计，开发时可显式选择草稿预览；再做普通 Markdown 解析、章节分块、来源元数据保存与 Chroma 正式索引。用开发题比较向量基线和组合检索，再完成带引用、证据不足处理的只读问答。固定配置后执行验收题，分别保留真实模型结果与人工核验；最后才在 M4 接入受控库存工具、持久提案确认和业务执行。

首版继续采用通用症状范围，不把具体车型资料作为启动 M3 的阻塞条件。PDF/DOCX/TXT 解析可利用既有库存制度语料验证，本轮不生成重复格式副本。不新增具体品牌、车型或未经核准的厂家件号。
