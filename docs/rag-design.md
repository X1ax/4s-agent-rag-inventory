# RAG 知识服务实现设计

设计日期：2026-10-23。状态：M3.1文本解析、M3.2向量检索、M3.3原生PDF/DOCX解析已完成，见 [M3.1](m3-1-verification.md)、[M3.2](m3-2-verification.md)、[M3.3验收](m3-3-verification.md)。阅读对象为后续开发、调试和验收模型。本文确定 M3 的实施顺序，不代表后续问答接口已上线。最新用户要求与 AGENTS.md 优先。

## 1 本阶段目标与边界

M3 提供两类只读知识服务：库存制度问答与通用车辆故障辅助排查。用户能够检索真实片段、展开来源、识别草稿/版本与适用限制；证据不足时获得明确反馈。故障入口不要求品牌、具体车型或年款，只在影响排查分支时追问系统结构和发生条件。

M3 不调用库存写服务、不对外下单，也不实现 LangGraph 提案确认。实时库存、实际补货/调拨建议和业务办理留给 M4；M3 可解释制度公式，并对用户明确提供的假设输入进行只读确定性复算。手册不能成为实时库存、价格、交期或实物适配的事实来源。

设计时仅交付方案；后续M3.1已在不新增依赖、不修改数据库和源资料、不调用模型的范围实现受控文本解析。其余阶段继续按授权逐步实施，不提前创建模块空壳或提交Git。

## 3 关键方案选择

| 决策 | 首版方案及理由 |
| --- | --- |
| 框架 | 直接使用现有 FastAPI、HTTPX、Chroma 和 Pydantic；不再引入通用 RAG 框架或模型适配层 |
| 来源管理 | 受控文件和清单是事实来源；本地不可变索引代次记录解析状态，不新增 MySQL 文档表 |
| 导入入口 | 首版采用本机显式 CLI，停后端后构建，Embedding仍通过在线API；页面可查询状态和问答，不提供任意文件上传、URL抓取或在线编辑发布 |
| 部署 | 一个 FastAPI 工作进程持有本地 Chroma；CLI与服务互斥访问，暂不支持多进程共享路径 |
| 更新 | 小规模语料全量构建新代次，验证后原子切换；不原地删改正在查询的集合 |
| 检索 | 先保留纯向量基线，再加编码精确匹配与字符词项检索，使用排名融合；暂不加重排序模型 |
| 对话 | 首版单轮问答；追问时前端将已确认条件与新问题组成明确输入，不建立隐式长期记忆 |
| 发布 | 默认只查已生效资料；草稿须显式预览且持续显示状态，不由管理员角色或聊天宣布批准 |

受控文件方案适合当前19份本地资料，能避免关系库、文件和向量库三方状态同步。它的明确边界是单进程与离线维护；实际需要多人在线维护、审批和持续导入时，再设计文档版本表及 Chroma 服务端部署，不提前建立通用工作流。

Chroma 官方将本地持久客户端用于本地开发和测试，服务化部署另有客户端/服务端方式；本项目采用前者匹配当前本地目标，不把它表述为生产高可用方案。[客户端说明](https://docs.trychroma.com/reference/python/client)

## 4 总体流程

~~~mermaid
flowchart TD
    S[受控原生文件与清单] --> P[解析与来源校验]
    P --> U[条款或完整故障条目]
    U --> B[显式在线Embedding]
    B --> G[新代次 Chroma 与片段快照]
    G --> V[核验并切换活动代次]
    Q[登录用户的问题与知识范围] --> F[来源新鲜度与发布过滤]
    V --> F
    F --> R[向量基线或组合检索]
    R --> C[去重并补充必要上下文]
    C --> A[受证据约束的单轮回答]
    A --> J[结构与引用校验]
    J --> O[回答 引用 状态 限制]
~~~

原生文件与清单负责来源事实，派生片段负责可复现解析，Chroma 负责候选召回，服务端负责范围、权限、确定性计算与引用校验。模型不能修改这些边界。

## 5 来源、发布与解析状态

### 5.1 三类状态分开保存

**来源批准状态：** 保留 inventory 的 approval_status 和 diagnostics 的 review_status 原值；当前统一归入 draft。将来只有登记实际审核/批准依据、生效范围、起止条件及版本替代关系后才能归入 released，不能仅改一个布尔值假称核准。技术复核与经营制度批准分别处理。

**派生处理状态：** pending、parsing、parsed、indexing、indexed、failed、needs_review。仅解析、来源完整性和索引校验均成功才可标 indexed。源清单中的 index_status 是当前资料记录，运行时状态取代次报告，不在构建中回写源清单造成来源哈希变化。

**查询资格：** knowledge_scope 为 released_only 或 draft_preview。indexed 不等于生效。released_only 必须同时满足真实批准记录、default_retrieval_enabled为true、来源有效、未撤回、范围相符及生效时间条件；draft_preview 只对显式选择的当前待复核资料开放，不把默认关闭标记改成生效，也不得包含已撤回/被替代资料或自动回退到历史版本。

当前默认查询应得到 no_eligible_documents；显式草稿预览才可检索现有正文。这是正确的发布控制，不能为让页面有答案而自动把草稿升级。

### 5.2 来源限制与版本冲突

每个来源以 knowledge_base、document_id、document_version 和原生 SHA256 共同识别。相同ID与版本出现不同内容时拒绝覆盖，要求显式提升版本并复核；不要仅以文件名、时间戳或“版本号较大”决定权威性。

首版每个清单中的同一 document_id 只允许一个当前候选版本，旧版本由历史代次保存。后续需要同时适用多个合同版本时，应扩展明确的订单/日期适用条件；条件缺失时回答 conflict，不自行平均交期或拼接条款。

首版没有仓库专属知识资料，不强加仓库过滤；仓库数量是实时数据。资料以后出现有效仓库/供应商适用范围时，应先扩展元数据及过滤测试，不靠正文中的相近名称猜测范围。

## 6 原生解析与内容校验

所有文件路径从固定清单解析，resolve 后必须仍在所属语料根目录内，拒绝路径穿越及指向 .env、其他项目或任意外部目录的链接。先校验文件类型、存在性、清单哈希、ID、版本和重复项，再读内容。读取失败时返回具体文档状态，不启动默认下载或静默改读母稿。

| 格式 | 处理方式与定位 |
| --- | --- |
| TXT / MD | UTF-8读取；分离元数据、文档说明、章节、条款/条目、表格；按实际标题和ID定位 |
| DOCX | 使用 python-docx 按正文原有次序遍历段落与表格，保留表头、行列关联和章节；引用条款与表格序号，不虚构页码 |
| PDF | 使用 pypdf 逐页提取文本并保留实际文件页号；依据登记条款和章节重建正文，跨页条款保留起止页 |
| 扫描/复杂文件 | 无可用文字层、表格关系不明、修订内容未决或提取缺失时进入 needs_review；首版不做OCR |

DOCX 不能先拼全部段落再把所有表格放末尾，否则会破坏上下文；官方 iter_inner_content 可按文档顺序给出段落与表格。[DOCX 文档对象](https://python-docx.readthedocs.io/en/latest/api/document.html)

PDF 不具有天然的段落和表格语义，pypdf 也不负责OCR，因此不能把“抽到了文字”当作表格关系已正确。[PDF 文本提取](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)

首版只承诺已登记、可验证的项目资料格式。表格必须能保留表头与对应行关系；当前两份PDF的表格需建立原生解析样例，关系不能可靠恢复时阻止该文档进入活动代次。不得用 authoring 中的Markdown代替PDF解析后仍声称读取了PDF。

校验至少覆盖制度219个条款ID、故障23个章节ID、唯一性、完整正文、适用条件和原生表格上下文。清理页眉/页脚只能按识别出的重复结构处理，不通用删除数字或短行。格式解析所需 pypdf、python-docx 在实际进入该步骤时加入项目依赖并锁版本；桌面捆绑运行时只用于资料检查，不能成为应用的隐含依赖。

## 7 分块与元数据

### 7.1 检索单元和回答上下文

制度以一个完整条款为检索单元，附文档标题、说明与章节路径。所在章节为父上下文，包含同章节条件和表格；召回条款后可补充父上下文，不能把相邻条款伪称为原条款内容。

故障以一个完整症状条目为检索单元，保留“适用与追问、故障类型、检查路径、换件判断、依据与限制”五部分。DX-GEN-001 的8条规则分别索引，同时作为故障问答必需的公共上下文。类型映射只作校验和图片导航，不产生新的技术证据。

不采用固定字数滑窗作为首版默认方案，也不跨文档/版本拼块。暂定单元上限4000字符，超过时进入人工分块复核，不能直接截断。上下文扩展预算不足时，优先减少条目数量，不切断一个故障条目的换件限制。字符上限是项目资源约束，不冒充模型token计数。

### 7.2 片段记录

| 字段组 | 必须保存 |
| --- | --- |
| 身份 | knowledge_base、document_id、document_version、source_sha256、unit_id、chunk_id |
| 定位 | title、section_path、clause_ids或section_ids、page_start/page_end（仅PDF真实页号）、table定位（如适用） |
| 正文 | 原生提取的unit_text、父上下文parent_id、可重建的context_text、embedding_text_sha256 |
| 状态 | 来源状态、生效信息、适用范围、parser_version、chunking_version |
| 追踪 | generation_id、Embedding模型/维度指纹、导入时间、错误与复核信息 |

chunk_id 为以上来源身份、单元ID及解析/分块版本的稳定哈希，不能只用数组下标。源内容、版本或处理规则变化必须产生可区分的ID；未变化输入重建时保持可比性。generation_id 标识一次完整索引代次，不作为替代来源版本的字段。

向量库只保存过滤和定位所需的扁平字段及检索正文；嵌套范围、完整表格和父上下文保留在代次JSON快照。缺少页码时不写虚构页号；缺少实际规格时不填默认数量。

## 8 索引构建、更新与撤回

### 8.1 本地存储约定

以下为待实现布局，全部位于现已忽略的 data/chroma 下：

~~~text
data/chroma/rag/
  owner.lock
  active.json
  generations/<generation_id>/
    generation.json
    sources.json
    units.jsonl
    contexts.jsonl
    chroma/
~~~

generation.json 保存源清单及原生哈希、解析/分块版本、模型服务与模型标识指纹、1024维校验、距离方式、数量核对、状态和时间。故障来源登记与类型映射也保存哈希并参与代次兼容性检查，但不当作技术正文嵌入；这些辅助资料变化后须复核重建，不能无声替换回答依据。指纹不包含密钥；不存带认证信息的URL。词项索引可从units在进程中重建，无需另建搜索服务。

### 8.2 构建流程

1. CLI取得本地独占所有者锁。M3.2仅CLI访问Chroma，当前业务后端不访问索引，可以保持运行。M3.5接入问答服务时，后端生命周期必须取得同一锁，离线构建与索引服务互斥；只支持一个索引工作进程，不能通过多个uvicorn worker绕过约束。
2. 读取并验证来源。首个MD/TXT阶段只选择已支持格式，报告未支持文档，不能冒称全19份已建索引；原生解析阶段完成后才构建完整代次。
3. 生成不可变单元和父上下文，检查来源与全部预期ID。相同完整构建指纹且已有合格活动代次时返回 no_change，不重复调用Embedding。
4. 分批显式请求在线Embedding，按返回index关联输入，检查数量、维度、有限值和非零向量，再写入新代次自己的Chroma路径。
5. 核验片段/向量数量、ID集合、过滤元数据、PDF定位和恢复读取，并再次确认源清单、原生文件及辅助资料哈希与构建开始时一致；全部成功后写 generation 状态 validated。
6. 在同一磁盘内先写活动指针临时文件，再通过原子替换切到新代次。失败不指向半成品；代次报告保留失败阶段与脱敏原因。
7. 启动后端时打开活动代次并核对兼容性。禁止在普通应用启动时自动全量Embedding、修复源文件或重置索引。

当前SDK 1.5.9支持 create_collection 的 configuration 与显式 embedding_function 参数。实现时指定 cosine、embedding_function=None，并在 add/query 中传入向量，不依赖 query_texts 触发默认模型。服务商Embedding接口支持显式模型与输入数组；请求长度以服务限制和本地预算共同约束。[Embedding API](https://siliconflow.readme.io/reference/createembedding)

M3.2构建批大小16条，HTTPX各网络操作超时30秒、单次构建共用一次重试预算；它不是严格的整批墙钟截止。查询网络操作超时10秒、不自动重试。发生重试则token总量标记不可用，因为失败请求可能已被计费。401/403、模型不存在、格式或维度错误不重试。未完成构建重试可重新构建新代次，不引入断点任务队列。M3.5仍需实现整次ask截止预算。

### 8.3 旧片段失效与故障恢复

每次请求先固定一个活动代次和来源资格快照，并核对当前清单与原生哈希。文件被修改、移除或撤回时，即使新索引尚未成功，也要立即从向量、词项、精确匹配和上下文扩展的候选范围排除相应旧来源，不允许以“旧索引还在”继续回答。

若只剩部分有效文档，报告部分不可检索；若公共规则失效，暂停整个故障问答。返回回答前再次核对实际使用来源与发布状态，发生变化时返回409 knowledge_changed，不展示已失效的生成内容。来源哈希检查成本随当前小规模文件量增长，后续有证据再优化，不能用缓存过期窗口放宽撤回要求。

失败的新代次不影响未变更来源的旧代次服务。回滚也必须重新通过当前来源/发布和模型兼容性核验，不能恢复已经撤回的知识。历史代次和失败文件只允许停后端、持锁后维护；首版不做运行中垃圾回收或删除正在查询的集合。

Chroma 对本地共享路径的并发写进程有限制，且已有向量不会因更换模型配置自动重嵌入；相同维度也不证明不同模型向量兼容。本方案以所有者锁、隔离路径与重建保证这一边界。[系统约束](https://cookbook.chromadb.dev/core/system_constraints/)

## 9 检索策略

服务端先按用户身份、知识域、知识范围、当前来源哈希和版本资格得到允许的文档集合；空集合直接返回，不调用Embedding。所有召回分支和上下文扩展使用同一集合，不能仅对最终展示结果做过滤。[Chroma 元数据过滤](https://docs.trychroma.com/docs/querying-collections/metadata-filtering)

### 9.1 向量基线

只对问题显式生成1024维查询向量，在允许来源内作cosine查询，保存距离与排序。首版默认候选20、最终k=5（请求范围1至10），实际数量不得超过允许片段数；这些均为待用开发集验证的初值。距离不当作概率，也不硬编码“相似度大于0.8一定可回答”。

### 9.2 组合检索

在相同来源与分块条件下，增加完整条款/章节ID精确匹配，以及标题、正文、术语的字符词项检索。中文以双字词项、英文以单词和完整编码建立简单TF-IDF权重，使用标准库计数即可；暂不增加分词模型或外部全文搜索。

对向量与词项候选按 RRF 排名融合，起始常数60，各分支候选各20条，按chunk_id去重并稳定排序。分数仅供排序，不作为置信度。问题显式要求某条款时，组合模式优先保留该精确条款；不存在、被过滤或失效时明确无法定位，不用相近编号替代。

内部登记的条款ID可以按其明确的大写规范匹配；厂家件号保留原样与符号，不能随意把AB-12变AB12。字符检索中的文本归一化不能变成部件身份等价规则。向量基线不偷偷加入精确匹配，以便如实比较组合检索的增益。

### 9.3 上下文组织

最终k按原始检索单元计数，去重后补充同章节父上下文；显式“参照某制度”的链接最多扩展一层且同样检查资格。缺少被引用制度时保留缺口，不能用文档编号生成并不存在的内容。

故障问答额外附DX-GEN-001公共规则；不把必带规则当作症状召回成绩。总证据预算暂定12000字符，扩展超预算时减少低排名条目并记录缺失；不能静默截掉限制后断言证据完整。

记录原始top-k与扩展后证据集。主要检索指标在原始单元上计算，上下文扩展覆盖另报，避免用整章扩展把漏检藏起来。回答可以引用实际提供的扩展条款，但必须标明它是扩展来源而非原始召回。

## 10 回答、引用与确定性复算

### 10.1 非计算问答

先查证据，再向现有Chat Completions兼容接口发起一次有界请求。不启用工具、联网或代码执行；文档、问题中的引用和附件均为不可信数据，不是权限指令。模型不接受系统身份、文件路径、批准状态和执行动作的客户端覆盖。

普通文本JSON经Pydantic校验，不默认使用尚未验证的供应商原生结构化响应能力。输出由 answer_status、claims、follow_up_questions、limitations 组成；claims每项含text与citation_ids。服务端将引用ID映射回实际片段与定位；不存在、跨代次、不可用的引用一律拒绝，不“补上一个看起来合理的来源”。

有事实结论而无对应证据时不能标answered。缺条件用needs_clarification；依据不足用insufficient_evidence；版本/适用冲突用conflict；实时库存问题用requires_live_data。无可用现行资料由服务端返回no_eligible_documents；范围外或不可信操作请求分别用outside_scope或refused。

结构和引用ID校验只能保证来源存在，不能自动证明语义被支持；仍需固定评测与人工核验。首版格式失败直接报明确错误，不无限修复重试。草稿范围回答始终带状态，前端不能隐藏该提示。

### 10.2 数值问题

模型不得自由生成补货量、调拨量或日期答案。对于用户明确提供的假设输入，可以返回 calculate_example 分支而非完整结论，包含计算类型、逐字段输入与对应原文出处。服务端检查类型、单位、非负整数/必要日期、完整统计区间和缺失条件，并确认输入出处存在于本轮问题；不能从制度示例、旧对话或模型常识偷取真实参数。

只实现评测需要的四种纯函数：补货公式、调拨数量守恒、完整自然日区间、给定顺序的可调量分配。Decimal/Fraction及整数计算负责向上取整和数量结果，服务端模板输出输入、步骤、结论与公式来源，不再让模型改写计算结果，因此仍只需一次模型请求。

输入提取中的出处校验不等于语义完全正确，需评测字段归属、单位和顺序；歧义时追问而非猜。前提只能表述为“按你提供的假设”，不声称已核实业务事实。这些纯计算不读取/锁定库存、不创建提案，也不冒充M4实时建议服务。

### 10.3 故障辅助排查

复用DX-RULE-06输出约定，增加fault_types、checks和part_decisions。部件状态只允许undetermined、not_indicated、conditional、recommended，逐件说明依据与成立条件。part_type_key只允许映射白名单，未收录类型为空并说明缺项，不能映射相似商品。

M3没有车辆检测工具，recommended必须明确归因于本轮用户提供的检查记录，并保留原文出处和真实性限制；症状、报码或用户推测不能伪装成检测事实。系统能检查引用/出处存在，不能自动认证维修报告真实。安全分流和换件结论仍按故障评测单独核验。

仅凭通用排查不能确定实际商品适配、单次需求、库存是否充足或生成领用。知识页面可以展示对应类型图片，但不显示“已确认可装车”的按钮或声明。

## 11 API 约定

M3.5已实现以下只读接口；聊天接口补充见本文件末尾。所有接口复用current_user，管理员、库管、经理均可读取同一内部知识范围；身份与角色由服务端取得。草稿预览是显式查询范围，不授予发布或业务审批权限。首版无写索引HTTP接口。

| 方法与路径 | 用途 |
| --- | --- |
| GET /api/knowledge/status | 活动代次、来源/处理状态计数、兼容性、配置是否存在；不测试收费接口 |
| GET /api/knowledge/documents | 资料列表、版本、格式、来源状态、处理状态及可检索原因；按知识域与范围筛选 |
| POST /api/knowledge/retrieve | 返回原始检索单元、允许的上下文、排序与定位；保留向量/组合模式供受控评测 |
| POST /api/knowledge/ask | 检索、受约束回答/假设复算与引用；不执行库存业务 |
| GET /api/knowledge/chunks/{chunk_id} | 在指定generation_id与知识范围下查看允许片段；路径由服务端映射 |

retrieve与ask共享请求字段：

~~~json
{
  "question": "按草案，调拨已发出但尚未收货时，目标仓可以领用吗？",
  "knowledge_base": "inventory_policies",
  "knowledge_scope": "draft_preview",
  "top_k": 5,
  "retrieval_mode": "hybrid"
}
~~~

question长度1至2000字符；knowledge_base只允许inventory_policies或general_diagnostics；低层知识接口默认knowledge_scope为released_only；retrieval_mode省略时按当前知识域选择：inventory_policies为hybrid，general_diagnostics为dense（2026-10-25后的实现）。显式模式仍可用于固定比较；2026-10-27当前结果见m3-m4-stability-verification.md。Pydantic拒绝未知字段，接口不接受任意SQL、URL、磁盘路径、操作人、发布状态或客户端指定的原始模型提示词。显式过滤文档时只接收服务端已登记ID且限制数量，不扩展权限。

回答例子的定位字段如下，文字只是接口设计样例，不是模型实测：

~~~json
{
  "request_id": "<server-generated>",
  "generation_id": "<active-generation>",
  "knowledge_scope": "draft_preview",
  "answer_status": "answered",
  "claims": [
    {
      "text": "按待核准草案，调拨发出后目标仓现有量尚不增加，在途不能领用。",
      "citation_ids": ["<provided-evidence-id>"]
    }
  ],
  "citations": [
    {
      "citation_id": "<provided-evidence-id>",
      "document_id": "INV-TRF-006",
      "document_version": "1.0-draft.1",
      "chunk_id": "<stable-unit-hash>",
      "unit_id": "INV-TRF-006-C007",
      "title": "跨仓调拨与在途交接规程",
      "source_state": "draft"
    }
  ],
  "follow_up_questions": [],
  "limitations": ["资料待核准；本回答未查询实时库存或办理调拨。"]
}
~~~

PDF引用另带真实起止页，其他格式不写页码；excerpt由服务端返回原文，不由模型编造。API不泄露绝对路径、认证URL或密钥。片段接口只提供当前有效代次的允许内容；索引已切换时返回409 citation_outdated，页面提示重新提问，不把旧引用悄悄换成新版本。

错误保留当前前端能读取的detail字符串，另加稳定error_code与request_id。401/403沿用现有认证；422为输入错误；409为来源变化或过期引用；503为索引/Embedding/模型未配置或不可用；504为请求超时；502为上游响应或模型结构非法。无证据、缺条件、需要实时数据属于200下的明确业务回答状态，不伪装成上游错误。

## 12 配置、超时、日志与页面

实现时在Settings绑定现有API_KEY、BASE_URL、MODEL_ID以及三项EMBEDDING配置，密钥使用SecretStr。Embedding不静默复用对话密钥；用户当前分别配置，沿用对应接口。未配置AI不影响普通库存API启动。

暂定ask总截止45秒，其中查询Embedding至多10秒、生成至多30秒，其余阶段共用剩余预算；单次ask不自动重试模型，以免隐性重复计费。构建使用独立批处理预算。最终模型上下文和输出token限制须依据实际服务配置验证，不能把字符数当token数。

现有前端api.js固定15秒，会导致AI请求过早中断；实际开发时为该函数增加可选的单请求超时参数，仅知识问答调用使用50秒，其余业务保持原15秒。超时只表示未取得回答，不能声明后端一定未请求模型。提交期间禁用重复发送，错误持续显示并允许显式重试。

新增一个KnowledgePanel.vue，沿现有App.vue菜单接入。页面只展示知识域、范围、问题、回答、引用、资料状态及操作所需限制；高级排序分数不混入业务结论。草稿选择明确提示待核准，不能默认勾选。需要明确加载、无现行资料、无命中、需补条件、冲突、失败和过期引用状态；引用展开显示原文与真实定位，故障候选保持类型与换件状态区分。

认证仍依赖现有数据库身份核验；“不改业务数据库”不等于知识接口可以绕过登录。已有/api/health和/api/ready语义保持不变，知识可用性由单独status表达。

正常日志只记录request_id、服务端用户ID、知识域/范围、代次、返回片段ID、阶段耗时、错误码和可获得的token用量；不默认持久保存完整问题/报告，不输出凭据或上游原始错误体。评测只记录明确的合成输入和脱敏输出。首次实现不建立会话数据库、后台任务队列或完整对话审计体系。

## 15 评测判定与发布门槛

库存与故障各自报告开发/验收结果，不合并成一个“总准确率”。主要配置包括源锁、问题文件哈希、模型与Embedding标识、代次、分块与父上下文规则、k、检索方式、过滤与生成设置。需要改题时先说明用途和版本，不能反复用冻结验收调参。

库存按规定证据组覆盖率与完整证据问题命中率统计，验收35题有检索目标、1题单列发布过滤；故障按其README的问题证据命中口径，公共规则与范围外题另报。分别保留top-k检索单元与上下文扩展后的证据；这些指标不自动等于全部相关片段Recall@k。

发布必须满足来源/权限/引用隔离、确定性复算和禁止写入等关键检查；在固定验收输入中出现伪造当前库存、草稿冒充生效、泄露凭据或未经确认写入时，不得用普通题均分抵消。一般检索效果目标在开发集实测基线后确定并冻结，再运行验收，不在没有结果时预填百分比。

语义支持、必要条件与故障换件判断需要人工核验，不能仅让同一模型自评。Mock结果、真实在线调用、解析成功、资料发布和完整M3验收分别登记。当前缺少企业批准与维修技术复核不阻止明确草稿范围的开发，但不能把草稿服务称为已正式核准的企业知识服务。
