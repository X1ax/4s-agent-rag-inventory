# 低库存采购办理及库存关注更新（2026-10-28）

## 实际办理结果

用户要求通过智能助手对所有低于安全库存的备件采购，并提交系统等待审核。本次全程在助手会话“低库存备件采购单拆分”中发起、生成提案并确认创建草稿，随后在审核中心提交；未用手工新建采购单页面、直接API或SQL创建业务单据。

每张采购单只能对应一个收货仓，因此两仓分别建单，同单每行可使用不同供应商。按安全库存缺口补货，扣除该收货仓有效采购待收和目标调拨在途；本次45项缺口记录的待收与在途均为0，均使用默认供应商有效供货报价及版本1。

## 实际操作暴露的问题与修复

助手首次回答的缺口项数、金额汇总错误，曾错误建议按供应商拆单；后续出现两次工具调用结构或白名单校验错误。采用分步目录查询、按仓核对与提案办理后完成，不能把本轮结果称为一次成功的无人干预批量采购。

实际提案卡片出现所有行显示首个备件的缺陷：新建明细不含`purchase_line_id`，原实现用其空值匹配同样没有`line_id`的第一条摘要。修复为仅在存在明确收货行ID时按ID匹配，普通新建明细按自己的`part_id`显示。先以真实失败形态复现测试（新建采购多行误用第一个SKU），再修复；另保留收货按原采购行ID匹配的回归测试。早期提案已拒绝，不产生业务单据。后续采购按实际提案卡片逐行核对及整数分复算，未采信助手自然语言中的错误合计。

修改位于`frontend/src/AgentProposal.vue`、`frontend/src/proposalRows.js`，没有改变审批权限、业务执行或库存逻辑。

## 库存关注的仓库归属与筛选

按用户后续要求，所有低库存卡片显示该仓库的调拨在途与采购待收货。直接使用现有`balance_statement()`返回的仓库-备件数据：采购只按`Document.warehouse_id`统计已确认/部分收货的未收量；调拨只按`target_warehouse_id`统计已发出未收货量。草稿、待审核采购、取消余量、未发出或已收货调拨均不纳入有效待到货。

新增“仅看计入在途、待收后仍不足”复选框，条件为`quantity + in_transit + purchase_pending < safety_stock`，严格小于；先过滤全部低库存记录再分页，切换时回到第1页。保持每页12条。快修仓不会使用主仓采购待收或目的地为主仓的调拨在途。

本次两张待审核采购尚未形成有效采购待收，因此低库存卡片相应待收仍为0；不得为了展示效果将其改成已确认或混入待收数量。

验证：16项前端测试通过、构建通过；4项MySQL统计测试通过，包含同一备件跨仓隔离、部分收货后的剩余待收、目标仓调拨在途，以及草稿采购/未发出调拨排除。页面实际检查数量展示、复选框与分页复位。截图：`docs/screenshots/stock-attention-incoming-20261028.png`。保留现有打包体积提醒。未提交Git。
